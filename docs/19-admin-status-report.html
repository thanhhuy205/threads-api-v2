Highlights

  • Frame-first implementation. Admin routes now have typed external DTOs and internal input interfaces, while service orchestration remains intentionally marked as TODO for later business logic.
  • Repository stays data-access focused. Repositories expose DB create/find/update/count/aggregate methods; they do not decide moderation outcomes such as approve, hide, or delete.
  • Dedicated BullMQ queue added. Auto-remove-ban has its own queue, producer, queue events file, and worker so it can be monitored separately from like/email/bloom/pinecone jobs.
  • No old HTML docs were removed. This file was added as a new report and linked from the docs hub.

Auto-Remove-Ban Queue Flow

No per-user delayed job is added at ban time. Current frame uses one hourly scanner. If later service logic needs immediate delayed remove-ban per user, add that job at the end of the ban service after DB commit.
