How the Circle module is structured

The Circle module follows Clean Architecture: requests enter via circle.routes.ts, pass through CircleController for input/output mapping, delegate to CircleService for business logic (permission checks, transaction orchestration), and finally reach three repositories — circleRepository, circleMemberRepository, and circleInvitationRepository — each responsible for its own Prisma model.

Callstack walkthrough

1
src/modules/circle/circle.routes.ts

Defines 5 routes: GET / (list circles), POST / (create), GET /request-invitation (user's invitations), POST /send-invitation, POST /response-invitation. Protected routes use authorization middleware and validate(schema) for Zod validation.

circleRouter.get('/', circleController.getCircle);
circleRouter.get('/request-invitation', authorization, circleController.getRequestInvitation);
circleRouter.post('/', authorization, validate(createCircleSchema), circleController.createCircle);
circleRouter.post('/send-invitation', authorization, validate(sendInvitationSchema), circleController.sendInvitation);
circleRouter.post('/response-invitation', authorization, validate(responseInvitationSchema), circleController.acceptInvitation);
2
src/modules/circle/controller/circle.controller.ts

Controller is thin: extracts req.user?.sub for auth, req.body for data, delegates to CircleService, and uses response helpers (res.paginate(), res.success(), res.error()). No business logic lives here.

show source 
// controller/circle.controller.ts — sendInvitation
async sendInvitation(req, res) {
  const userId = req.user?.sub;
  if (!userId) return res.error(401, "Unauthorized");
  const { circleId, userId: targetUserId } = req.body;
  await circleService.sendInvitation({ circleId, userId: targetUserId, inviterId: userId });
  return res.success(200, `Invitation sent...`);
}
3
src/modules/circle/service/circle.service.ts

The brain of the module. sendInvitation checks: (1) user not already a member, (2) inviter has ADMIN/OWNER role, (3) resend limit ≤ 5, then wraps upsert in a transaction. acceptInvitation branches on status: REJECTED → only update status; ACCEPTED → update status + create CircleMember, both inside transactionService.doInTransaction.

show source 
// service/circle.service.ts — acceptInvitation (hot path)
if (data.status === CircleInvitationStatus.REJECTED) {
  return await transactionService.doInTransaction(async (tx) => {
    await circleInvitationRepository.rejectInvitation(data.circleId, data.userId, tx);
  });
}
return await transactionService.doInTransaction(async (tx) => {
  await circleInvitationRepository.acceptInvitation(data.circleId, data.userId, tx);
  return await circleMemberRepository.create({ circleId: data.circleId, userId: data.userId }, tx);
});
4
src/modules/circle/repository/circle-invation.repository.ts

circleInvitationRepository handles all invitation DB operations: upsert (create or re-invite rejected users with resentCount++), findInvitationById (PENDING only), acceptInvitation (status → ACCEPTED, reset resentCount), rejectInvitation (status → REJECTED). All mutation methods accept a tx: Prisma.TransactionClient parameter.

show source 
// repository/circle-invation.repository.ts — upsert
async upsert(data, tx = prisma) {
  return tx.circleInvitation.upsert({
    where: { circleId_userId: { circleId: data.circleId, userId: data.userId }, status: "REJECTED" },
    update: { resentCount: { increment: 1 }, inviterId: data.inviterId, status: "PENDING" },
    create: { circleId: data.circleId, userId: data.userId, inviterId: data.inviterId, status: "PENDING" },
  });
}
5
prisma/schema.prisma — Circle, CircleMember, CircleInvitation

Three models back the module. Circle has a publicId (cuid) for cursor pagination and a Visibility enum. CircleMember uses a composite unique @@unique([circleId, userId]) and a RoleMembership enum (OWNER/ADMIN/MEMBER). CircleInvitation adds resentCount and CircleInvitationStatus (PENDING/ACCEPTED/REJECTED).

show source 
// prisma/schema.prisma
model CircleInvitation {
  id          Int                    @id @default(autoincrement())
  circleId    Int                    @map("circle_id")
  userId      String                 @map("user_id")
  inviterId   String                 @map("inviter_id")
  resentCount Int                    @default(0) @map("resent_count")
  status      CircleInvitationStatus @default(PENDING)
  // ... relations, indexes
  @@unique([circleId, userId])
}

Key files

  • circle.routes.ts 5 endpoints, Zod validation, auth middleware.
  • controller/circle.controller.ts Thin I/O layer, delegates to service.
  • service/circle.service.ts Permission checks, TX orchestration, business rules.
  • repository/circle.repository.ts Circle CRUD, cursor pagination via findAll.
  • repository/circle-invation.repository.ts Invitation upsert, accept, reject with TX support.
  • repository/circle-member.repository.ts Member creation, role lookup by circleId.

Gotchas

  • The upsert in invitation repo has where: { status: REJECTED } — it only re-invites rejected users, not pending ones. A pending user gets an error, not a duplicate row.
  • createCircle auto-creates a CircleMember with role ADMIN for the creator via nested Prisma create. Don't create the member separately.
  • findInvitationById filters by status: PENDING — accepted/rejected invitations won't be found, which prevents double-accept bugs.
  • The resentCount limit (5) is hardcoded in the service, not configurable.
